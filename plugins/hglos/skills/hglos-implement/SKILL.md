# HGLOS Implement - 구현 레그

## 역할

승인된 계획서를 **구현자가 바로 움직일 수 있는 지시서**로 바꾸고, 구현을 진행시키고, 보고서를 받아 검증 레그로 넘긴다.
기본 형태는 이 세션이 오케스트레이터가 되어 작업별 서브에이전트(또는 Codex)에 맡기는 것이다. 누가 구현했는지 보고서에 적는다.

## 시작 조건 - 하나라도 아니면 멈춘다

1. 계획서 **승인란이 채워져 있다** (범위·계획 둘 다, 사람의 승인 발화 인용 포함). 비어 있으면 hglos-design 으로 돌려보낸다.
   `Current State` 첫 줄의 "승인 시점 커밋"(H)과 지금 계획서를 대조한다:
   - H 는 승인란(계획 칸)이 채워진 커밋이어야 한다 - `git show H -- <계획서>` 에 승인란 변경이 보여야 한다
   - 해시 줄은 H 바로 다음 커밋에서 한 번 적히고 **이후 바뀌지 않는다.** `git log -L` 또는 `git log -p -- <계획서>` 로
     그 줄이 두 번 이상 바뀌었으면 멈춘다 (해시 줄을 새 커밋으로 옮겨 적으면 승인 후 변경이 감춰진다)
   - `git diff H -- <계획서>` 에 `Current State` 절 밖의 변경이 있으면 **승인 후 바뀐 계획서다.** 멈추고 재승인을 받는다
   이 커밋들은 사람이 승인한 커밋이다. 모델이 실행하더라도 사람의 명시적 지시가 있어야 하고, 승인란·해시 줄을 스스로 고쳐 커밋하지 않는다.
2. 계획서의 전제 표에 **결과가 빈 칸이 없다**.
3. 정본이 지정돼 있으면 **지금 그 판을 다시 확인한다.** 정본 확인의 유효 기간은 확인한 그 시점까지다.
4. **이 세션이 계획서를 쓴 맥락이 아니다.** 계획서를 쓴 세션이면 새 세션(오케스트레이터)에서 시작한다. 승인란을 채운
   직후 같은 맥락에서 구현으로 넘어가면 설계자가 자기 설계를 구현·판정하게 된다.

## 1. 지시서 만들기

`assets/instruction-template.md` 의 8절을 순서대로 채운다. 순서에 의미가 있다.

핵심 규칙:

- **게이트와 승인을 분리한다.** 게이트는 **미달일 때만** 사람을 부른다. Step 마다 승인을 받지 않는다 -
  "각 Step 완료 시 짧게 보고하고 다음으로 진행하라"를 지시서에 적는다. Step 마다 승인을 받으면 게이트가 아니라 동의 절차가 된다.
  **단, 계획서 작업 필드가 이 기본값보다 우선한다:**
  - `oracle: none` 인 작업 - 기계 판정이 없으므로 **변경 단위마다 사람이 본다.** 지시서 8절에 그렇게 적는다
  - `tier: T2` 인 작업 - **착수 전에** 사람 확인을 받는다. 그 뒤 진행 중에는 미달일 때만 부른다
- 게이트는 **두 곳에 적는다**: 해당 Step 본문(★)과 8절 진행 규율 목록. 실행자는 Step 에서, 사람은 8절에서 본다.
- **Step 0 = 전제 재측정**: 계획서 전제의 "실행 환경" 칸과 지금 환경이 다르면(버전·OS·도구가 바뀌었으면) 그 전제를 다시 잰다.
  전제가 **좋은 쪽으로 바뀌어도 보고하게** 적는다. 설계가 그 전제 위에 서 있으므로 변화 자체가 정보다.
- **임계값을 숫자에 맞추지 마라**를 해당 Step 에 문장으로 적는다. 세는 방법을 명시하고 근거를 남기게 한다.
- **개수·집합 주장은 스크립트 출력으로** 보고하게 한다 (`scripts/set_diff.py`). 눈으로 센 숫자는 근거가 아니다.
- **정본과 충돌하면 임의로 결정하지 말고 보고하라**를 적는다.
- **커밋은 전체 완료 후 사람 승인을 받아 한 번에.** `git add -A`·`commit -a` 금지.

## 2. 병렬 실행

계획서 작업 분할에 병렬 판정 결과가 있으면 그대로 따른다. 없거나 사용자가 "병렬로 해줘"라고 하면 지금 판정한다:

```
python <이 스킬>/scripts/check_parallel.py <tasks.json> --repo <repo>
```

- **가능**: 이 세션이 **오케스트레이터**가 되어 작업마다 **새 서브에이전트**를 띄우고, 작업별 지시서를 따로 준다.
  지시서의 쓰기 범위 밖을 건드리지 말라고 적는다. 오케스트레이터는 직접 구현하지 않고 결과를 모은다.
  사람이 별도 세션을 손으로 여는 방식은 기본값이 아니다 - 세션끼리 결과를 못 주고받아 사람이 중계하게 된다(실측).
  별도 세션·worktree 는 작업이 서브에이전트 하나에 안 들어갈 만큼 길 때만 쓴다.
- **보고 원문은 오케스트레이터가 파일로 저장한다**: `<산출 폴더>/report-<작업>.md`. 서브에이전트가 파일을 못 쓰는
  하네스가 있다(실측). 대화에만 있는 보고는 세션과 함께 사라진다.
- **조건부**: 조건(보통 공유 계약 동결)을 먼저 끝낸 뒤 병렬로 간다.
- **불가**: 직렬로 간다. 겹친 범위를 사용자에게 그대로 보여준다.
- **동시 실행 수는 상한(기본 3) 안에서.** 사용량과 사람의 검토 부담이 같이 늘어난다.
  상한은 서브에이전트가 다시 띄우는 하위 에이전트까지 센다. 지시서에 "하위 에이전트를 띄우지 마라" 또는 허용 수를 적는다.
- **git 에 안 보이는 공유 자원**(배포 폴더, 장비 설정 등)에 닿을 수 있는 묶음은 오케스트레이터가 묶음 **전후로 직접**
  해시 스냅샷을 남기고 대조한다. 스냅샷은 slice 산출 폴더(예: `<repo>/validation/<slice>/run/`)에 둔다. 작업자가 기록하면 자기가 오염시킨 것을 자기가 기록하게 된다. 다르면 다음 묶음으로 가지 않는다.
- 단계는 위에서 아래로 순서대로, 동시에 도는 것은 한 단계 안의 작업뿐이다. 선후 의존(`after`)은 스크립트가 단계에 반영한다.
- **병렬 작업은 대장 파일에 쓰지 않는다** (미결 목록, 우려 목록, 진도표). 보고서에 "등록 제안"으로만 적고,
  합친 뒤 한 작성자가 반영한다. 동시에 쓰면 나중 쪽이 앞 편집을 조용히 덮는다.
- 합친 뒤 **통합 검증 1회**를 hglos-verify 모드 B 로 요청한다. 작업별 통과는 통합 통과가 아니다.
- 병렬로 돌린 회차는 보고서에 동시 수, 작업별 소요, 통합 충돌 수를 적는다 (상한·하한 조정의 근거).

## 3. 보고서 받기

`assets/report-template.md` 형식. 구현자가 쓰고, 이 세션은 빠진 절만 확인한다.
특히 **"확인하지 못한 것"이 비어 있으면 되묻는다** - 비어 있으면 "전부 확인했다"로 읽힌다.

## 4. 넘기기

보고서가 갖춰지면 hglos-verify 에 넘긴다. **검증자는 구현 맥락을 공유하지 않는 새 서브에이전트(또는 새 세션)**이고,
누구로 할지는 hglos-verify 의 검증자 우선순위를 따른다. 오케스트레이터 자신이 판정하지 않는다.

계획서의 `Current State` 절을 갱신한다. 별도 핸드오프 파일을 만들지 않는다.

## 되돌아가는 경우

- **구현 중 실측이 계획서 전제를 반증했다** → 멈추고 설계로 되돌린다. 무효가 된 계획대로 코드를 넣지 않는다.
- 그 외의 설계 재논의는 구현 후에 받지 않는다. 받으면 게이트가 두 번이 되고 핑퐁이 시작된다.

## 절대 금지

- 승인 전 계획서로 시작
- 오라클 경로 수정 (계획서 `oracle` 필드의 경로). 수정 흔적이 있으면 그 실행은 무효
- 종결 선언 - 종결은 검증 레그 판정 + 사람 승인
- 커밋을 사람 승인 없이
- 병렬 작업이 쓰기 범위 밖을 건드리기

## 참조

- `assets/instruction-template.md` - 구현자 지시서 8절
- `assets/report-template.md` - 구현 보고서
- `scripts/check_parallel.py` · `set_diff.py` - 판정 스크립트
